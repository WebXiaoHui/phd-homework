# 任务一：节点分类实验报告

> 框架：PyTorch Geometric 2.0.4 + PyTorch 2.3.1 + CUDA 12.1
> 硬件：NVIDIA GeForce RTX 3070 Ti (8 GB)，Windows 11 + WSL2 (Ubuntu 22.04)
> 数据来源：`graph_beginner-main/任务一_节点分类/results/results.jsonl`（共 35 条记录），
> 统计汇总见 `实验报告/_原始数据/图神经网络_结果汇总.md`。本报告所有数值均取自该台账，未做任何补造。

---

## 1. 任务目标

对应作业 [任务一、节点分类](../../graph_beginner-main/README.md) 的四条要求：

1. 基于现有图神经网络框架（DGL / PyTorch Geometric）实现图上的节点分类；
2. 使用 Cora、Citeseer、Flickr 三个数据集；
3. 测试 GCN、GAT、GraphSAGE、GIN 四种模型；
4. 利用框架自带的 Sampler 采样子图进行训练，并与全图训练进行**性能**和**运行时间**的对比。

同时对应作业「报告要求」的 3.1（不同神经网络、不同学习率、不同网络层数对性能的影响）与
3.2 中属于本任务的部分（全图训练 vs 分批次训练）。

**节点分类的定义**：给图上少量节点（Planetoid 数据集是每类 20 个）的标签，预测其余节点的类别。
与任务三（图分类）的区别在于：本任务的样本单位是「节点」，输入始终是**一张大图**；
任务三的样本单位是「一张图」。

## 2. 数据集与实验设置

### 2.1 数据集

| 数据集 | 节点数 | 边数 | 特征维度 | 类别数 | 划分方式 |
|---|---|---|---|---|---|
| Cora | 2,708 | 10,556 | 1,433 | 7 | Planetoid 官方划分：140 训练 / 500 验证 / 1,000 测试 |
| Citeseer | 3,327 | 9,104 | 3,703 | 6 | Planetoid 官方划分 |
| Flickr | 89,250 | 899,756 | 500 | 7 | 代码自行按类分层随机划分，`seed=42` 固定 |

Cora / Citeseer 使用 PyG 自带的官方划分，可与论文结果直接对照；Flickr 是 PyG 把原多标签
数据整理成的 7 类单标签任务，**没有官方划分**，因此由代码按类别分层后随机切分，随机种子固定为 42
以保证可复现。Flickr 的规模约为 Cora 的 33 倍，是三个数据集中唯一真正需要子图采样才能放进显存的数据集。

### 2.2 模型

四个模型共用同一套骨架：**若干层消息传递 + 一层线性分类头**，只替换消息传递层。
代码实现详见 `任务一_节点分类/code/models.py`：

| 模型 | 聚合方式 | 代码 |
|---|---|---|
| GCN | 按度数固定的加权平均，权重不学习 | `GCNConv` |
| GAT | 8 头注意力，权重由模型学出 | `GATConv(heads=8, concat=True)` |
| GraphSAGE | 自身特征与邻居均值拼接后再变换，均值聚合 | `SAGEConv(aggr="mean")` |
| GIN | 邻居求和 + 2 层 MLP，`ε` 可学习 | `GINConv(train_eps=True)` |

### 2.3 超参数（均来自 results.jsonl 记录字段）

| 参数 | 取值 | 说明 |
|---|---|---|
| `layers` | 2 | 消息传递层数（层数消融另取 3、4） |
| `hidden` | 128 | 隐藏层维度 |
| `dropout` | 0.5 | |
| `lr` | 0.01 | 默认学习率（学习率消融另取 0.001 / 0.005 / 0.05） |
| `weight_decay` | 5e-4 | |
| `epochs` | 150 | 所有主实验与消融实验统一 150 轮 |
| `seed` | 42 | |
| 采样模式 `batch_size` | Cora/Citeseer 128；Flickr 4096 | |
| `num_neighbors` | [10, 10] | 每层每节点采 10 个邻居 |

采样批量之所以按数据集分开设置，是为了让「每轮参数更新次数」不至于退化：Cora 训练节点仅 140 个，
`batch_size=128` 时每轮更新 2 次；Citeseer 训练节点 120 个，每轮仍只有 1 次更新；
Flickr 训练节点约 8.9 万，`batch_size=4096` 时每轮更新 11 次。这一点直接决定了下面
「性能 vs 时间」的分析必须同时看 `steps_per_epoch`。

### 2.4 训练 / 验证 / 测试流程

本任务**没有单独的 `test.py`**。`train.py` 是一条龙脚本：

```
读数据、划分 train/val/test
→ 每轮在训练集上训练、在验证集上评估
→ 记录验证指标，变好就把模型参数存快照
→ 训练结束后，用「验证集最优轮次」的参数在测试集上评估一次
→ 把全部超参与 best_val_acc / best_test_acc / best_epoch 等追加写入 results/results.jsonl
```

选用验证集最优轮次而非最后一轮，是因为训练后期会过拟合：训练损失继续下降而验证指标开始变差。
用验证集挑轮次是标准做法；**测试集只在最后使用一次**，不参与挑轮次，避免信息泄漏。

### 2.5 评价指标

`best_val_acc`（验证集最优准确率）与 `best_test_acc`（用该轮参数在测试集上的准确率），
另记录 `best_epoch`（验证最优发生于第几轮）。耗时字段包括
`train_time_per_epoch`（每轮纯训练秒数，已剔除第 1 轮的 CUDA 初始化开销）、
`train_time_total`、`wall_time`（含评估的墙钟时间）和 `steps_per_epoch`（每轮参数更新次数）。

- 台账共 **35 条记录**，全部 `tag` 为空，即全部为正式实验记录，没有调试/对照记录混入。

## 4. 结果分析

以下所有倍数/百分点均由第 3 节表格中的原始数值直接计算得到。

### 4.1 模型对比（性能）

- **Cora**：`full, lr=0.01, L=2` 下 GraphSAGE 最好（0.7840），GCN 次之（0.7790），
  GAT 0.7700，GIN 最差 0.7550。即便把采样模式算进来，GraphSAGE + sample 的 0.8180 仍是全台账最高。
- **Citeseer**：GraphSAGE 最优（0.6830），GAT 0.6770，GCN 0.6740，GIN 0.6240。
  与 Cora 相比整体低 10 个百分点左右，符合该数据集「特征更稀疏、边更少」的特点。
- **Flickr**：GAT 0.5237 ≈ GraphSAGE 0.5244 ≈ GCN 0.5233，三者差距在 0.11 个百分点以内，
  基本处于同一水平；GIN 全图模式只有 **0.4234**，明显掉队。
- **GIN 在节点分类上确实不稳**：这与任务 README 的预判一致（「GIN 是为图分类设计的，
  用在节点分类上通常不如 GCN/GAT 稳」）。Flickr 全图 GIN 的验证最优轮次是第 22 轮（0.4239），
  远早于其他模型的 124~145 轮，说明它在当前超参下很早就停止改进。

### 4.2 全图 vs 子图采样：性能（分开谈）

**结论一：小数据集上采样训练不一定更差，Cora 上反而全面更好。**

Cora 四个模型的采样 test_acc 全部高于全图，提升幅度：

| 模型 | full | sample | 变化 |
|---|---|---|---|
| GCN | 0.7790 | 0.8030 | **+2.40 个百分点** |
| GAT | 0.7700 | 0.7980 | **+2.80 个百分点** |
| GraphSAGE | 0.7840 | 0.8180 | **+3.40 个百分点** |
| GIN | 0.7550 | 0.7640 | +0.90 个百分点 |

原因有两层：(1) 每轮只看局部子图，相当于一种正则化，缓解了小数据集上的过拟合；
(2) Cora 训练节点 140 个、`batch_size=128`，采样模式每轮有 **2 次**参数更新而全图只有 1 次，
150 轮下来采样多走了一倍的梯度步。

**结论二：Citeseer 上采样反而更差，因为「多走步」的好处没有兑现。**

| 模型 | full | sample | 变化 | steps/epoch |
|---|---|---|---|---|
| GCN | 0.6740 | 0.6490 | **−2.50 个百分点** | 1 → 1 |
| GAT | 0.6770 | 0.6800 | +0.30 个百分点 | 1 → 1 |
| GraphSAGE | 0.6830 | 0.6730 | −1.00 个百分点 | 1 → 1 |
| GIN | 0.6240 | 0.6400 | +1.60 个百分点 | 1 → 1 |

Citeseer 训练节点只有 120 个，`batch_size=128` 比训练节点还大，采样模式每轮**同样只更新 1 次**。
此时采样没有带来任何「更新更频繁」的收益，只剩下「每层只采 10 个邻居」的信息损失，所以 GCN、GraphSAGE
出现 1~2.5 个百分点的下降。这与任务 README 中记录的现象完全一致。

**结论三：Flickr 上采样对 GIN 是救命，对其他模型只是打平。**

Flickr 全图 GIN 的 test_acc 只有 0.4234，采样后升到 0.5113（**+8.79 个百分点**），是全部对比中
变化最大的一项——采样打散了全图训练里 GIN 因求和聚合导致的数值/梯度问题。
而 GCN（0.5233 → 0.5041，−1.92 pt）、GAT（0.5237 → 0.5166，−0.71 pt）略降，
GraphSAGE 略升（0.5180 → 0.5241/0.5244，+0.61/+0.64 pt）。四个模型在 Flickr 上的准确率
聚集在 0.51~0.52 附近，与数据集本身标签噪声较大有关（7 分类随机猜为 14.3%）。

### 4.3 全图 vs 子图采样：时间（与性能分开谈）

**结论四：在本实验规模下，采样训练省的是显存，不是时间——Flickr 上每轮慢 73~171 倍。**

Flickr 每轮耗时对比（采样每轮 11 次更新，全图 1 次）：

| 模型 | 全图每轮秒 | 采样每轮秒 | 每轮倍数 | 全图单步秒 | 采样单步秒 | 单步倍数 | 总训练秒倍数 |
|---|---|---|---|---|---|---|---|
| GCN | 0.0146 | 2.0273 | **138.9×** | 0.0146 | 0.1843 | 12.6× | 305.71 / 2.419 = **126.4×** |
| GAT | 0.0293 | 5.0075 | **170.9×** | 0.0293 | 0.4552 | 15.5× | 752.63 / 4.811 = **156.4×** |
| GraphSAGE | 0.0889 | 6.8580 | **77.1×** | 0.0889 | 0.6235 | 7.0× | 1025.84 / 13.731 = **74.7×** |
| GIN | 0.0513 | 3.7444 | **73.0×** | 0.0513 | 0.3404 | 6.6× | 562.02 / 7.965 = **70.6×** |

GCN 的 2.0273 s/轮 vs 0.0146 s/轮（慢 138.9 倍）是最直观的例子。
**为什么「采样更快」的直觉在这里失效？** 两者的瓶颈完全不同：

- **全图训练**的瓶颈是 GPU 计算，但模型很小（2 层、128 维），Flickr 的稀疏矩阵乘法在 GPU 上
  只要 0.0146 秒，GPU 远未吃满；
- **采样训练**的瓶颈是 **CPU 构图**。PyG 的 `NeighborLoader` 在 CPU 上做采样、拼子图，
  每批 4096 个种子节点经两跳采样后子图约 4.5 万个节点，仅组装子图就要 2~7 秒，GPU 全程等待。

因此更准确的表述是：**子图采样用时间换显存**。只有整张图大到放不进显存、
或全图计算的耗时超过 CPU 采样开销时，采样训练才有时间优势。

**结论五：Cora 上采样的「每轮更慢」主要来自每轮多走一步，单步开销其实很接近。**

Cora 采样每轮 2 次更新，若折算到单步：

| 模型 | 全图每轮 | 采样每轮 | 每轮倍数 | 全图单步 | 采样单步 | 单步倍数 |
|---|---|---|---|---|---|---|
| GCN | 0.0032 | 0.0083 | 2.59× | 0.0032 | 0.00415 | 1.30× |
| GAT | 0.0093 | 0.0156 | 1.68× | 0.0093 | 0.00780 | **0.84×（更快）** |
| GraphSAGE | 0.0027 | 0.0129 | 4.78× | 0.0027 | 0.00645 | 2.39× |
| GIN | 0.0045 | 0.0139 | 3.09× | 0.0045 | 0.00695 | 1.54× |

**这正是必须先看 `steps_per_epoch` 的原因**：只比较「每轮耗时」会得出「全图一律更快」的结论，
但 Cora 采样每轮做了两倍的更新。Citeseer 因为两种模式都是 1 步/轮，采样每轮仅慢 1.26~1.58 倍
（GCN 1.58×、GAT 1.50×、GraphSAGE 1.34×、GIN 1.26×），可以直接比较。

### 4.4 学习率的影响

- **Cora**：test_acc 随 lr 单调递增，0.001 → 0.7630，0.005 → 0.7740，0.01 → 0.7790，
  0.05 → **0.8090**。lr=0.05 比默认 0.01 高 **3.0 个百分点**，是全部 Cora 全图实验中的最好成绩；
  但它的最优轮次是第 95 轮，远晚于 lr=0.01 的第 8 轮，说明大学习率收敛更慢、更依赖完整的 150 轮预算。
- **Flickr**：几乎不敏感，四个学习率的 test_acc 落在 0.5172~0.5233 之间，极差仅
  **0.61 个百分点**，最优值是 lr=0.01（0.5233）。这与数据集本身难度高、模型容量相对不足有关，
  学习率不是主要瓶颈。
- 学习率对**耗时**基本无影响（Cora 各档每轮 0.0032~0.0081 s，Flickr 0.0146~0.0293 s），
  差异属于测量噪声量级。

### 4.5 网络层数的影响

- **Cora**：L=2 最优（0.7790），L=3 降到 0.7690，L=4 进一步降到 0.7530，
  **单调下降**，L=4 比 L=2 低 2.6 个百分点，是过平滑（over-smoothing）的典型表现：
  消息传递次数过多，所有节点的表示趋于一致，区分度下降。
- **Flickr**：趋势相反且幅度很小，L=2 0.5233 → L=3 0.5167 → L=4 **0.5287**，
  极差 1.2 个百分点。Flickr 上 L=4 略好，说明在该数据集上更深的感受野
  （4 跳邻居）带来了一点收益，但差距仍在噪声范围内。
- **层数显著增加时间与参数**：Cora 上 L=2→L=4，每轮从 0.0032 s 增至 0.0150 s（**4.7×**），
  参数从 184,711 增至 218,247；Flickr 上每轮从 0.0146 s 增至 0.0502 s（**3.4×**），
  参数从 65,287 增至 98,823。这与「层数增加会放大邻居子图规模与计算量」的预期一致。

## 5. 踩坑与经验

以下条目均出自项目/任务 README 中**已经记录并已在代码里处理**的结论，非本报告新推断。

1. **PyG 版本必须锁 2.0.4**：更新的 PyG 改了 import 路径与算子签名，例如
   `global_min_pool` 在 2.0.4 中不存在。本任务虽未用到 min pooling，但同一套 `models.py`
   的算子写法受此约束。
2. **GAT 多头注意力的维度**：8 个头拼接后输出维度是 `每头维度 × 8`。若误算成
   `隐藏维度 × 8`，后续 BatchNorm 会报 `running_mean should contain 32 elements not 256`。
   代码用 `_conv_out_dim()` 统一处理。
3. **分析全图 vs 采样必须同时看 `steps_per_epoch`**：本任务两种模式的每轮更新次数差
   最多达 11 倍（Flickr）或 2 倍（Cora），只比「每轮耗时」会得出错误结论。
   这是任务 README 专门强调的一条。
4. **「采样训练更快」是有条件成立的**：采样省的是显存而不是时间，本次实测中采样每轮反而
   慢 73~171 倍。采样真正的价值在于「当图大到全图放不进显存时，它是唯一可行的方案」——
   Flickr 的 8.9 万节点 × 500 维在此只要几百 MB，全图完全跑得动；若节点数是千万级，
   全图会直接 OOM。
5. **断点续跑用 `--skip_done`（默认开启）**：结果追加写 `results.jsonl`，
   重跑时按「数据集+模型+模式+学习率+层数+种子」自动跳过已完成实验。
   本任务主实验与 lr/层数消融的重叠配置（lr=0.01、L=2）正是因此未被重复记录，
   这也是 38 个设计条目最终只留下 35 条记录的原因。
6. **操作教训：「只看实验列表」必须加 `--dry_run`**：`run_all.py ... | grep` 不能只看不跑，
   管道只是隐藏输出，训练照常启动。
7. **操作教训：`pkill -f` 的模式要写窄**：宽松的 `pkill -f "run_all.py --stage"` 会
   误杀其他正在运行的任务，代码因此加了 `--skip_done` 以便中断后续跑。
8. **操作教训：杀掉壳进程后子进程可能变成孤儿继续跑**，需回头用 `nvidia-smi` 与
   `tasklist.exe` 确认没有残留的 python 进程。

## 6. 结论

1. 四个模型在 Cora / Citeseer 上都能复现出与文献相近的水平（Cora 最高 0.8180，
   Citeseer 最高 0.6830）；**GraphSAGE 在 Cora 与 Citeseer 上都是主实验最优模型**；
   Flickr 上 GAT / GraphSAGE / GCN 三者基本持平（0.5233~0.5244），GIN 明显偏弱（全图 0.4234）。
2. **采样 vs 全图在性能上没有单调结论，取决于「每轮是否多走了步」**：
   Cora（2 步/轮）采样全面更高（+0.9~+3.4 pt）；Citeseer（1 步/轮）采样略差
   （−2.5~+1.6 pt）；Flickr 上除 GIN 大幅改善外其余基本打平。
3. **采样 vs 全图在时间上的结论是明确的：本次规模下采样每轮慢 73~171 倍，
   总训练时间最多慢 156 倍**，瓶颈是 CPU 端的子图组装而非 GPU 计算。
   采样训练的价值是省显存与可扩展性，不是提速。
4. **学习率**：Cora 上 lr=0.05 最优（0.8090，+3.0 pt），Flickr 上基本不敏感（极差 0.61 pt）。
5. **层数**：Cora 上 L=2 最优且随层数单调下降（过平滑），Flickr 上差异在噪声内；
   但层数对耗时与参数量的放大是确定性的（Cora L2→L4 每轮 4.7 倍）。
6. 完成度：35 条记录对应 34 个唯一配置，学习率与层数消融均已跑完；
   唯一的数据瑕疵是 Flickr + GraphSAGE + sample 有两条同配置记录（结果差 0.03 pt）。

## 7. 复现命令

在 `任务一_节点分类/code` 目录下执行（以下命令抄自任务 README，未改动参数）：

```bash
# 单次实验（训练 + 验证挑轮次 + 测试一条龙）
python code/train.py --dataset Cora --model GCN --mode full

# 子图采样训练（Flickr 需指定 batch_size）
python code/train.py --dataset Flickr --model GAT --mode sample --batch_size 4096

# 批量跑全部对比实验（主实验 + 学习率 + 层数），150 轮
python code/run_all.py --stage all --epochs 150

# 只查看会跑哪些实验（务必加 --dry_run，不要用管道过滤）
python code/run_all.py --stage main --dry_run

# 生成图表与汇总表
python code/plot_results.py

# 检查数据集是否就绪
python code/prepare_data.py
```

单次实验的完整参数（默认值，来自 `utils.py` 的 `add_common_args` 与 `train.py`）：

```bash
    --dataset Cora --model GCN --mode full \
    --batch_size 1024 --num_neighbors 10 \
    --layers 2 --hidden 128 --dropout 0.5 \
    --lr 0.01 --weight_decay 5e-4 \
    --epochs 150 --eval_every 1 --seed 42
```
