## 1. 任务目标

对应作业 [任务四、知识图谱](../../graph_beginner-main/README.md) 的要求：

1. 参考 KGE 框架，基于参考资料与知识图谱补全框架，支持常见模型 **TransE、RotatE、ConvE**；
2. 了解三种模型的原理（TransE 平移、RotatE 旋转、ConvE 卷积）；
3. 了解数据集训练集/验证集/测试集的划分。

同时对应作业「报告要求」3.1 中「分析不同参数和不同的神经网络对性能的影响」：
- 不同神经网络 → `--stage main`（3 模型 × 2 数据集）；
- 不同参数 → **用 embedding 维度 `dim` 代替「网络层数」**（`--stage dim`），
  另做学习率消融（`--stage lr`）。

**知识图谱补全（链接预测）的定义**：知识图谱是一堆 `(头实体, 关系, 尾实体)` 三元组，
补全任务是已知 `(h, r, ?)` 或 `(?, r, t)`，给所有候选实体打分并把正确答案排到最前面。
与任务二（图上链路预测）的区别在于：任务二的边只有「有/无」，只学节点表示；
本任务的边带**关系类型**，需要同时学实体与关系的表示，并用专门的打分函数 `f(h, r, t)`。

## 2. 数据集与实验设置

### 2.1 数据集

| 数据集 | 实体数 | 关系数 | 训练 | 验证 | 测试 | 来源与特点 |
|---|---|---|---|---|---|---|
| WN18RR | 40,943 | 11 | 86,835 | 3,034 | 3,134 | WordNet，实体/关系少，每条关系对应实体多，**较好猜** |
| FB15k-237 | 14,541 | 237 | 272,115 | 17,535 | 20,466 | Freebase，关系有 237 种且非常细，很多关系在训练集只出现几次，**较难猜** |

（实体数/关系数与 results.jsonl 中每条记录的 `num_entities` / `num_relations` 字段一致。）

### 2.2 划分方式

数据文件自带 `train.txt` / `valid.txt` / `test.txt`，**代码不做任何重新划分**，直接使用官方划分：
训练集更新参数，验证集每若干轮评估一次并挑最优轮次，测试集最后只用一次。
这样可以防止数据泄漏——若用测试集选模型，测试结果就不可信了。

### 2.3 三个模型与打分函数

设头实体向量 `h`、关系向量 `r`、尾实体向量 `t`：

| 模型 | 打分方式 | 直觉 | 代码要点 |
|---|---|---|---|
| **TransE** | `score = -‖h + r − t‖₂` | 关系是平移向量 | 参数最少、最快 |
| **RotatE** | 复数乘法 `h ∘ r ≈ t`，`score = γ − ‖h ∘ r − t‖` | 关系是复平面上的旋转，`\|r\|=1` | 实体用 `dim*2` 维实数存（实部+虚部），关系只存 `dim` 个相位角 |
| **ConvE** | `(h‖r)` reshape 成 `10 × (2d/10)` → 2D 卷积 + BN + ReLU + Dropout → 全连接 → `x · t + bias_t` | 用卷积让 h 与 r 的不同维度产生更复杂交互 | 慢：评估要给每个候选实体过一遍卷积 |

默认 embedding 维度（`models.py` 的 `DEFAULT_DIM`）：TransE 500、RotatE 500、ConvE 200。
ConvE 要求 `2*dim` 能被 10 整除，因此 `dim` 取 5 的倍数。

### 2.4 损失函数与超参数（均来自 run_all.py 的显式设置与 results.jsonl 记录）

| 参数 | 取值 | 说明 |
|---|---|---|
| `loss` | **bce** | 负采样 + 二分类交叉熵；三个模型统一，对比最公平 |
| `num_neg` | 64 | 每条正样本抽 64 个负样本 |
| `lr` | **0.001** | KGE 必须用比 GNN 更小的学习率（通用默认 0.01 会让 embedding 剧烈震荡） |
| `weight_decay` | **0.0** | 对 KGE 必须为 0，通用默认 5e-4 是致命的（见第 5 节） |
| `batch_size` | 256 | 三元组小批量 |
| `margin` | 1.0 | `margin` 损失时才用 |
| `label_smoothing` | 0.0 | 负采样训练时关闭 |
| `epochs` | WN18RR 100 / FB15k-237 50 | WN18RR 三元组少多跑几轮，FB15k-237 数据多则少跑 |
| `eval_every` | 10 | 每 10 轮评估一次验证集 |
| `valid_limit` | 800 | 验证集最多评估 800 条（评估要「给所有实体排名」，很贵） |
| `seed` | 42 | |

`run_all.py` 里显式写死 `DEFAULT_LR = 0.001`、`DEFAULT_WD = 0.0` 并强制传给 `train.py`；
`KEY_FIELDS` 中额外包含 `weight_decay`，以防用错误权重衰减跑出的记录被误认为「已完成」。

### 2.5 评估指标（过滤式 + 方向平均）

对每个测试三元组 `(h, r, t)`：

1. 固定 `h, r`，给**所有实体**当尾实体打分排名 → 看 `t` 排第几；
2. 固定 `r, t`，给**所有实体**当头实体打分排名 → 看 `h` 排第几；
3. 两个方向取平均作为该三元组的排名。

| 指标 | 含义 | 方向 |
|---|---|---|
| **MRR** | 排名倒数的平均（第 1 名 1 分、第 2 名 0.5 分、第 10 名 0.1 分） | 越大越好 |
| **Hits@1 / @3 / @10** | 正确实体排进前 1 / 3 / 10 名的比例 | 越大越好 |
| **平均排名（mean_rank）** | 名次平均值 | **越小越好** |

两个容易忽略的细节：**（1）过滤式评估**：同一个 `(h, r)` 可能对应多个正确尾实体
（如 `(姚明, 出生于, 上海)` 与 `(姚明, 出生于, 松江)` 都对），评估前先把训练/验证/测试集中
其它同样正确的答案分数置成 `−inf`，否则正确名次会被白白拉低
（代码位置：`train.py` 的 `build_filter_index()` 与 `evaluate()`）。
**（2）方向平均**：业界都报「猜尾 + 猜头」两个方向的平均，只报一个方向无法与文献对比。
台账中同时记录了 `test_mrr_head` 与 `test_mrr_tail`，便于分析方向偏差。

### 2.6 训练 / 验证 / 测试流程

**没有单独的 `test.py`**。`train.py` 一条龙完成：
训练 → 每 `eval_every` 轮在验证集上算 MRR → 按验证 MRR 挑最优轮次并保存权重 →
用该轮参数在测试集上做过滤式评估 → 追加写入 `results/results.jsonl`。

### 2.7 为什么本任务没有「网络层数」和「全图 vs 分批」

**（1）没有「网络层数」——用 embedding 维度 `dim` 作为容量消融。**

作业报告要求 3.1 写的是「学习率、**网络层数**」，但本任务三个模型都不存在「层数」这个超参数：

- TransE 就是 `h + r ≈ t` 一个公式，没有层；
- RotatE 就是复数乘法 `h ∘ r ≈ t`，也没有层；
- ConvE 是「一层卷积 + 一层全连接」，加层数不是它的常规用法
  （`10 × (2d/10)` 这种小特征图上再加卷积层会立刻被卷没）。

因此在任务四里用 **embedding 维度 `dim`** 作为「网络容量」的等价消融（`--stage dim`，
候选 `{100, 200, 500}`），这也正是 KGE 领域参数敏感性实验的标准做法
（TransE / RotatE / ConvE 论文做的都是 dim）。

**（2）没有「全图 vs 分批次」——作业明确不需要，且概念上不成立。**

作业原文即写明「任务四不需要」。从原理上讲，知识图谱根本没有「整张图的邻接矩阵」这个概念：
实体靠三元组索引，训练本身就是对三元组做小批量随机梯度下降，不存在一个可以
「整图前向一次」的对象。所谓「全图」在 KGE 里对应的是「一次性给所有实体打分」，
那是**评估**（1-N 打分）而不是训练方式。因此台账中 11 条记录全部为 `batch_size=256` 的小批量训练，
没有也不应有 `mode` 字段。

### 2.8 实验分组与完成度（重要，如实记录）

| 分组 | 设计次数 | 台账实际条数 | 其中有效 | 说明 |

## 4. 结果分析

以下所有倍数/百分点均由第 3 节表格中的原始数值直接计算得到。

### 4.1 模型对比（性能）

- **WN18RR**：RotatE 最优（test_MRR **0.3128**，H@10 0.4655），是 TransE（0.1637）的
  **1.91 倍**（+14.91 个百分点 MRR，H@10 高 7.78 pt），ConvE 最差（0.0264）。
  RotatE 的 H@1 达 0.2336，而 TransE 只有 0.0407 —— 相差 **5.7 倍**，
  说明旋转建模把大量正确答案直接推到了第 1 名，这正是 RotatE 相对 TransE 的核心优势。
- **FB15k-237**：TransE 略优（test_MRR **0.2100**），RotatE 0.1919（低 1.81 pt），
  与 WN18RR 上的排序相反。FB15k-237 的关系有 237 种且高度细分，
  RotatE 的 40.9M（WN18RR）/14.7M（FB15k）参数量虽更大，但在 50 轮预算内没有体现出优势。
- **ConvE 在两个数据集上都接近随机**：WN18RR test_MRR 0.0264（H@10 0.0511）、
  FB15k-237 test_MRR 0.0025（H@10 0.0059）。ConvE 的 mean_rank 分别为 10590.1（实体数 40,943）
  与 6232.6（实体数 14,541），接近「随机排一半」的水平。
  **这与文献中 ConvE 在 FB15k-237 上通常优于 TransE 的结论严重不符。**
  需要如实说明：台账中只有这一组 ConvE 配置（bce、dim=200、50/100 轮）且没有对照实验，
  因此无法判定原因是训练轮数不足、负采样 BCE 与 ConvE 原生 1-N 打分不匹配，
  还是实现细节问题。**这是一个未解释的负面结果，必须补做对照后才能下结论。**
- **mean_rank 与 MRR 的排序不一致（值得注意）**：
  WN18RR 上 TransE 的 mean_rank（3193.9）优于 RotatE（3796.2），
  但 RotatE 的 MRR（0.3128）几乎是 TransE 的两倍。
  原因是 RotatE 把大量正确答案排进前列（H@1 0.2336 vs 0.0407），
  但少数极端靠后的错误把平均名次拉低。这正说明**评估 KGE 不能只看平均排名**，
  MRR 与 Hits@K 更贴近实际使用（用户只看前几个结果）。
- **「猜头」明显难于「猜尾」，且 FB15k-237 上差距最大**：

  | 数据集 | 模型 | test_MRR_head | test_MRR_tail | tail/head |
  |---|---|---|---|---|
  | WN18RR | TransE | 0.1709 | 0.1565 | 0.92 |
  | WN18RR | RotatE | 0.2864 | 0.3393 | 1.18 |
  | FB15k-237 | TransE | 0.1399 | 0.2801 | **2.00** |
  | FB15k-237 | RotatE | 0.1124 | 0.2714 | **2.41** |
  | FB15k-237 | ConvE | 0.0007 | 0.0043 | 6.14 |

  WN18RR 的两个方向基本均衡（0.92~1.18），而 FB15k-237 上「猜尾」的效果是「猜头」的
  2.0~2.4 倍。这与 FB15k-237 含大量「多对一」关系（许多头实体共享同一个尾实体，
  如性别、国籍一类）相符：在这种情况下给定关系与尾实体去反推头实体本身就存在歧义。
  **这也说明只报单一方向会掩盖问题，方向平均是必要的。**

### 4.2 embedding 维度（容量）的影响

**（1）TransE：dim 从 100 增到 500，性能提升明显，代价可接受。**

同为 12 轮、同为 `weight_decay=0`，WN18RR + TransE 的对比：

| dim | test_MRR | H@10 | mean_rank | 每轮秒 | 总训练秒 | 参数量 |
|---|---|---|---|---|---|---|
| 100 | 0.0832 | 0.2176 | 10477.7 | 1.90 | 23.1 | 4,095,400 |
| 500 | **0.1342** | **0.3902** | 9046.6 | 3.50 | 42.1 | 20,477,000 |

- test_MRR 提升 **61.3%**（0.1342/0.0832 = 1.613），H@10 提升 **79.3%**（1.793 倍），
  平均名次从 10477.7 改善到 9046.6；
- 代价是参数量扩大到 **5.00 倍**（20.48M / 4.10M），每轮耗时只扩大到 **1.84 倍**（3.50/1.90），
  总训练时间 42.1 s vs 23.1 s（**1.82 倍**）。
  **这是一笔划算的交易**：时间只多花 82%，MRR 提升 61%。注意耗时增长（1.84×）
  远小于参数增长（5.00×），因为 KGE 的瓶颈主要在负采样打分与排序，而非参数量本身。
- 注意两条记录的 H@1 都是 **0.0000** —— 12 轮的短跑还不足以把答案排到第 1 名，
  因此这两条只能用于比较 dim 的相对趋势，不能当作最终性能。

**（2）RotatE：dim=200 反而优于 dim=500，与 TransE 的方向相反。**

| dim | epochs_run | best_epoch | val_MRR | test_MRR | H@1 | H@10 | 每轮秒 |
|---|---|---|---|---|---|---|---|
| 200 | 10 | 10 | 0.5025 | **0.4571** | 0.4218 | 0.5233 | 4.31 |
| 500 | 100 | **10** | 0.3071 | 0.3128 | 0.2336 | 0.4655 | 8.10 |

这两次运行的 **best_epoch 都是第 10 轮**，因此可以在此轮次上做相对公平的比较：
dim=200 的 test_MRR（0.4571）比 dim=500（0.3128）高 **46.1%**，H@1 高 **80.6%**
（0.4218 vs 0.2336）。更关键的是，dim=500 在 100 轮里**再也没有超过第 10 轮**，
说明对 RotatE 而言过大的维度在 WN18RR 上会过早进入过拟合/退化区间，
而 dim=200 既更好又更省（参数量 16.38M vs 40.95M，每轮 4.31 s vs 8.10 s）。

**综合来看，「容量越大越好」在 KGE 上不成立**：TransE 的最优维度偏向大（500 > 100），
RotatE 在本设置下偏向小（200 > 500）。这与两个模型的参数量结构有关——
RotatE 每个实体用 `dim*2` 维实数存储，dim=500 时参数量已达 40.95M，
是 TransE dim=500（20.48M）的 **2.00 倍**，对 8.6 万条训练三元组而言明显偏大。

### 4.3 时间对比（与性能分开讨论）

**（1）模型层面：ConvE 比 TransE 慢一个数量级，且没有换来精度。**

| 数据集 | 模型 | 每轮秒 | 相对 TransE | 总训练秒 | 折算分钟 | 参数量 |
|---|---|---|---|---|---|---|
| WN18RR | TransE | 2.99 | 1.00× | 299.0 | 5.0 min | 20,477,000 |
| WN18RR | RotatE | 8.10 | **2.71×** | 809.8 | 13.5 min | 40,948,500 |
| WN18RR | ConvE | 24.60 | **8.23×** | 2460.3 | **41.0 min** | 10,178,327 |
| FB15k-237 | TransE | 4.95 | 1.00× | 247.7 | 4.1 min | 7,389,000 |
| FB15k-237 | RotatE | 16.39 | **3.31×** | 819.6 | 13.7 min | 14,659,500 |
| FB15k-237 | ConvE | 62.45 | **12.62×** | 3123.0 | **52.1 min** | 4,916,725 |

- ConvE 的每轮耗时是 TransE 的 8.23 倍（WN18RR）到 12.62 倍（FB15k-237），
  单次训练需要 41~52 分钟，而 TransE 只要 4~5 分钟。
  原因是 ConvE 打分要「把每个候选实体与关系一起过一遍卷积」。
  项目 README 也提示「ConvE 的实验会明显卡住不动，那是正常的」。
  **结果是：ConvE 花掉最多的时间，却拿到最低的 MRR（0.0264 / 0.0025）。**
  需要说明的是，ConvE 的参数量其实并不大（10.18M / 4.92M），
  时间开销来自**结构性的卷积计算量**而不是参数规模。
- **RotatE 的总训练时间在两个数据集上几乎相同**（809.8 s vs 819.6 s），
  尽管 FB15k-237 的训练三元组是 WN18RR 的 3.13 倍
  （272,115 / 86,835）。原因在于轮数设置不同：WN18RR 跑 100 轮、FB15k-237 只跑 50 轮，
  而每轮耗时 8.10 s → 16.39 s 正好是 **2.02 倍**，与轮数减半相互抵消。
- **TransE 每轮耗时随数据规模的增长低于三元组数量增长**：
  FB15k-237 比 WN18RR 多 3.13 倍训练三元组，但每轮只慢 **1.66 倍**（4.95 / 2.99），
  说明小批量训练的开销并不与三元组总数线性相关（每轮只遍历一个 batch 的子集）。

**（2）维度层面：时间与参数的扩张不同步。**

TransE dim 100 → 500：参数量 ×5.00，每轮耗时仅 ×1.84，总训练时间 ×1.82
（表见 4.2 节）。这意味着在本实验的规模下，**增大 embedding 维度是「低时间成本、高精度收益」的操作**，
比换更复杂的模型（如 TransE → RotatE，每轮 ×2.7~3.3）更划算。

### 4.4 关于「网络层数」与「全图 vs 分批」

见 2.7 节的原理说明。这里补充数据层面的印证：
台账 11 条记录的 `batch_size` 全部为 256，没有 `mode` 这类字段，
也没有任何层数相关字段；本任务不存在「全图训练」这一对照条件。
`fig2_dim_effect.png`（维度影响）与 `fig3_lr_effect.png`（学习率影响）虽已生成，
但由 2.8 节可知 **`dim` 只有 3 条记录、有效 `lr` 记录为 0 条**，
因此这两张图只能作为「已有数据的可视化」，**不足以支撑完整的维度/学习率消融结论**。

### 4.5 权重衰减与学习率的作废对照说明了什么

同为 WN18RR + TransE + dim=100 + **12 轮**、仅 `weight_decay` 不同：

| weight_decay | val_MRR | test_MRR | H@10 | mean_rank | best_epoch |
|---|---|---|---|---|---|
| 5e-4（通用默认值，**错误**） | 0.0086 | 0.0074 | 0.0155 | 20635.7 | 9 |
| **0.0（正确设置）** | **0.0936** | **0.0832** | **0.2176** | **10477.7** | 12 |

验证 MRR 相差 **10.9 倍**（0.0936 / 0.0086），test_MRR 相差 **11.2 倍**，
test H@10 相差 **14.0 倍**（0.2176 / 0.0155）。
而且从外部看**没有任何异常**：损失没有变成 NaN，程序正常跑完，只是结果安静地变成垃圾。
项目 README 还记录了一次更极端的实测（同样 12 轮，`5e-4` 时验证 MRR 低到 **0.0007**，
与 `0` 时的 0.0936 相差 **130 倍**）。
这正是这类 bug 最危险的地方——**它成功地产出了一份看起来正常的错误结果**。

另一条 `verify` 记录（dim=500、`lr=0.01`、`wd=5e-4`、12 轮）的 val_MRR 只有 0.0047、
test_MRR 0.0024，且 best_epoch 仅第 4 轮。它同时叠加了错误的学习率与错误的权重衰减，
因此**不能用来单独判断学习率的影响**；台账无法据此给出任何学习率结论。

## 5. 踩坑与经验

以下条目均出自项目/任务 README 中**已经记录并已在代码里处理**的结论。

1. **⚠️ 权重衰减必须设成 0（最隐蔽的一条，因为它不报错）**：
   通用默认值 `weight_decay=5e-4` 对 KGE 是致命的，验证 MRR 可从 0.0936 掉到 0.0007
   （相差 130 倍），且不报错、损失不变 NaN。
   原因是 Adam 会把「权重衰减」这一项也归一化到 `lr` 量级，使它变成一个和真实梯度
   **一样大的、恒定把参数往 0 拉的力**，而 KGE 的参数几乎全是 embedding。
   代码已写死 `DEFAULT_WD = 0.0`，并把 `weight_decay` 加入 `KEY_FIELDS`，
   防止错误配置被当作「已完成」跳过。
2. **⚠️ 1-N 打分用在 TransE / RotatE 上会「虚假收敛」**：
   `--loss 1n` 训练 TransE 时损失降到 0.0168 看起来完美，但测试 MRR ≈ 0.0008（等于瞎猜）。
   原因是距离型模型只要把 `h + r` 推到无穷远（向量范数爆炸），
   就能让所有分数一起变低，损失瞬间下降，但模型没学到任何语义。
   RotatE 同理。ConvE 是内积型、分数有界，不受影响。
   因此默认统一用 `--loss bce`，三个模型一视同仁。
3. **⚠️ 负采样训练时不要开标签平滑**：标签从 `1/0` 改成 `0.9/0.1`，
   在每条正样本只配 64 个负样本时会给 BCE 引入下界
   `−0.9·ln0.9 − 0.1·ln0.1 ≈ 0.325`，模型学到这点区分度后损失再也降不下去
   （实测死死卡在 **0.3526**）。标签平滑只在 1-N 打分里有用。
   代码因此拆成两个参数：`--label_smoothing`（默认 0.1，仅 `loss=1n` 时生效）与
   `--neg_label_smoothing`（默认 **0.0**，`loss=bce/margin` 时生效）。
4. **学习率必须显式给 0.001，不能用通用默认值 0.01**：
   `utils.py` 的统一默认 `lr=0.01` 是给 GNN 的；KGE 的 embedding 是
   「每个实体一个自由向量、参数间无权重共享」，`lr=0.01` 会让 embedding 剧烈震荡、
   损失降不下去。`run_all.py` 显式传 `--lr 0.001`。
   **若直接手敲 `train.py` 而不经过 `run_all.py`，必须手动加上 `--lr 0.001 --weight_decay 0`。**
5. **验证集评估要限制条数**：评估要「给所有实体排名」很花时间，ConvE 还要对每个候选实体
   过一遍卷积，因此 `--valid_limit 800` 默认开启以加速验证。
6. **评估必须做过滤（filtered setting）并平均两个方向**：
   否则同 `(h, r)` 的其它正确答案会拉低名次；只报一个方向无法与文献对比。
7. **评估时分块计算**：任务二的 Flickr 测试集有 450 万条负样本，一次性计算需约 1 GB 显存，
   代码按 30 万条一块分块打分；本任务评估「全部实体」也采用类似的分块策略
   （`--eval_chunk`）。
8. **PyG 版本必须锁 2.0.4**：更新的 PyG 改了 import 路径与算子签名
   （例如 `global_min_pool` 在 2.0.4 中不存在）。
9. **不要并发跑多个任务**：项目 README 记录过实测教训——同时跑 3 个任务时，
   任务四的每轮耗时从 **3.24 秒膨胀到 728 秒**（慢 200 多倍），
   原因是显存不足退化到走 PCIe 的共享显存。**本任务必须单独跑。**
10. **操作教训**：`run_all.py` 只看列表必须加 `--dry_run`；中断用 `Ctrl+C` 而非
    `pkill -f run_all.py`；`--skip_done` 支持按「数据集+模型+dim+lr+loss+weight_decay+seed」断点续跑。
11. **统计实验结果不要把所有任务放进同一个进程**：四个任务的 `code/` 下都有同名的
    `datasets.py` / `utils.py` / `models.py`，同进程 import 会互相串味，
    导致统计数字完全错误。要统计就一个任务开一个进程，或用 `--dry_run`。

## 6. 结论

1. **WN18RR 最优模型是 RotatE（dim=500）**：test_MRR **0.3128**、H@1 0.2336、
   H@3 0.3496、H@10 0.4655、mean_rank 3796.2。它把 TransE（MRR 0.1637）提升了 **91.1%**，
   H@1 提升 **5.7 倍**，旋转建模对「多对多」关系的表达能力优势明确。
2. **FB15k-237 最优模型是 TransE（dim=500）**：test_MRR **0.2100**、H@1 0.1317、
   H@10 0.3681、mean_rank 284.8，略优于 RotatE（0.1919）。两个数据集的模型排序相反，
   说明「哪种 KGE 模型更好」依赖数据集的关系结构。
3. **ConvE 是明确未达预期的负面结果**：WN18RR test_MRR 0.0264、FB15k-237 0.0025，
   接近随机水平，却消耗了最多时间（每轮 24.60 / 62.45 s，单次训练 41 / 52 分钟）。
   台账中只有一组 ConvE 配置且无对照，原因（轮数不足？BCE 与原生 1-N 不匹配？实现问题？）
   尚不能判定，**必须补做对照实验**。
4. **容量消融（dim）表明「越大越好」不成立**：TransE 上 dim 500 优于 100
   （test_MRR 0.1342 vs 0.0832，+61.3%，时间只多 1.82 倍）；
   而 RotatE 上 dim 200 明显优于 500（在相同的 best_epoch=10 上 0.4571 vs 0.3128，+46.1%），
   大维度反而更早退化。
5. **权重衰减必须为 0 是本任务最重要的工程结论**：错误值 5e-4 使验证 MRR 从 0.0936
   掉到 0.0086（本台账，10.9 倍），README 记录过 130 倍的极端案例，且全程不报错。
6. **「网络层数」与「全图 vs 分批」在本任务不适用**：三个模型都没有层数超参数，
   故用 embedding 维度 `dim` 作为容量消融；知识图谱不存在「整图邻接矩阵」，
   训练天然是小批量三元组，作业也明确说明不需要该对比。
7. **完成度**：27 个设计条目实际完成 11 条，其中有效 9 条（主实验 6 + dim 对照 3）、
   作废 2 条。**`dim` 只完成 3/9，`lr` 有效记录为 0/12**，
   这是本任务最大的数据缺口：报告要求 3.1 中的「学习率影响」目前没有任何可用数据，
   「不同参数（dim）」的结论也只覆盖了 TransE 的两个维度和 RotatE 的一个维度。

## 7. 复现命令

在 `任务四_知识图谱/code` 目录下执行（以下命令抄自任务 README 与 `日志.md`，未改动参数）：

```bash
# 单次实验（训练 + 验证挑轮次 + 测试一条龙，走 run_all 时默认 lr/wd 正确）
python code/train.py --dataset WN18RR --model TransE

# 手动单独跑 train.py 时必须显式指定 lr 与 weight_decay（否则会用错误的通用默认值）
python code/train.py --dataset WN18RR --model TransE --dim 100 --epochs 3 \
    --eval_every 1 --valid_limit 200 --lr 0.001 --weight_decay 0

# 只打印配置、不训练、不写记录（任务四的 train.py 支持 --dry_run）
python code/train.py --dataset WN18RR --model TransE --dim 100 --epochs 3 \
    --lr 0.001 --weight_decay 0 --dry_run

# 批量跑全部对比实验（main 6 + dim 9 + lr 12 = 27）
python code/run_all.py --stage all

# 只跑某一组
python code/run_all.py --stage main     # 3 模型 × 2 数据集
python code/run_all.py --stage dim      # WN18RR 上的 embedding 维度消融
python code/run_all.py --stage lr       # WN18RR 上的学习率消融（当前有效记录为 0）

# 只查看会跑哪些实验（务必加 --dry_run）
python code/run_all.py --stage main --dry_run

# 生成图表与汇总表
python code/plot_results.py

# 检查数据集
python code/prepare_data.py
```

单次实验的完整参数（默认值，抄自任务 README）：

```bash
python code/train.py \
```
