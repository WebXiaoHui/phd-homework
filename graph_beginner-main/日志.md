## 1. 开跑前必读：三条铁律

### 铁律 1：一次只跑一个任务，别并发

你的显卡是 **RTX 3070 Ti，8 GB 显存**。

实测教训：同时跑 3 个任务时，任务四的每轮耗时从 **3.24 秒膨胀到 728 秒**（慢了 200 多倍）。
原因是显存不够，驱动把数据换到共享内存里去了，比直接算慢得多。

**所以：跑完一个任务再跑下一个。** 想省时间可以晚上睡觉前挂一个。

### 铁律 2：只想"看看会跑哪些实验"，一定要加 `--dry_run`

```bash
python run_all.py --stage all --dry_run      # ✅ 只打印，不训练
python run_all.py --stage all                # ❌ 直接开始训练！
```

**这个坑我自己踩过**：我本来只想数一数还剩多少实验，把输出管进了 `grep` 想过滤一下，
结果 `run_all.py` 照样在后台真的开始训练了 —— 管道只是把输出藏起来，进程并不会停。
所以**不要**用 `python run_all.py ... | grep xxx` 的方式去"看一眼"。

### 铁律 3：中断用 `Ctrl+C`，不要用 `pkill -f run_all.py`

```bash
Ctrl+C                                    # ✅ 在跑的那个窗口里按
pkill -f "run_all.py --stage"             # ❌ 会把你所有正在跑的任务一起杀掉
```

`pkill -f` 匹配的是**整条命令行**，一条宽松的模式会把别的任务的进程也一起匹配上。
（我早期用 `pkill -f run_all.py` 一次性杀掉了任务一和任务三正在跑的进度，这个教训写进根目录 README 了。）

如果确实要在别的窗口杀，**用精确的 PID**：

```bash
# 先看清楚是谁
/mnt/c/Windows/System32/tasklist.exe /FI "IMAGENAME eq python.exe"
# 确认命令行（把 <PID> 换成上面查到的号）
/mnt/c/Windows/System32/WindowsPowerShell/v1.0/powershell.exe -NoProfile \
    -Command "Get-CimInstance Win32_Process -Filter 'ProcessId=<PID>' | Select-Object -ExpandProperty CommandLine"
# 确认是自己的任务再杀
/mnt/c/Windows/System32/taskkill.exe /PID <PID> /F
```

> ⚠️ 杀掉壳进程后，**子进程可能变成孤儿继续跑**（占着显存和内存）。
> 杀完一定要回头确认一遍：`nvidia-smi` 里没有计算进程、`tasklist` 里没有 `python.exe`。

## 4. 跑到一半断了怎么办？（好消息：可以续跑）

**所有 `run_all.py` 都默认开启 `--skip_done`**：它会先读 `results.jsonl`，
把**已经跑完的配置跳过**，只跑剩下的。

所以你只要**重新敲一遍同样的命令**就行：

```bash
"$PY" run_all.py --stage all
```

它会打印一行 `[跳过] 有 N 个实验在 results.jsonl 里已经有结果了，本次不重复跑`。

**想全部推翻重跑**，加 `--no_skip_done`：

```bash
"$PY" run_all.py --stage all --no_skip_done     # 慎用，会把所有轮数重新烧一遍
```

**想知道现在还剩多少没跑**（只查看、不训练）：

```bash
"$PY" run_all.py --stage all --dry_run
```

最上面那行会写 `本次要跑 N/M 次实验`。

> 💡 **别自己写脚本把所有任务放在一个 Python 进程里统计**。
> 我踩过这个坑：四个任务的 `code/` 目录里都有同名的 `datasets.py` / `utils.py` / `models.py`，
> 放在同一个进程里 import 会**互相串味**（Python 会把第一个加载的模块缓存下来，
> 后面几个任务读到的其实是第一个任务的 `utils`），
> 导致统计出来的数字完全是错的（我当时看到"任务二 38/38 已完成"，
> 而它其实只跑了 17 个）。
> **要统计就一个任务开一个进程**，或者干脆用上面的 `--dry_run`。

## 5. 结果怎么看

每个任务的 `results/results.jsonl` 是**一行一个 JSON**，追加写入。
每个实验一行，里面既有超参数也有指标。

**通用字段**：`dataset`、`model`、`lr`、`seed`、`tag`、`best_val_metric`、`best_test_metric`、
`train_time_total`、`n_params` 等。

**每个任务特有的关键字段**（这几个是判断结果能不能用的重点）：

| 任务 | 字段 | 说明 |
|---|---|---|
| 任务一 | `mode` | `full`(全图) / `sample`(分批次) |
| 任务二 | `decoder` | `dot`(点积) / `mlp` |
| 任务三 | **`pool_norm`** | **必须是 `ln`**；如果是 `bn`，说明这条是旧的作废结果 |
| 任务三 | `pooling` | `avg` / `max` / `min` / `sum` |
| 任务三 | `mode` | `full` / `sample` |
| 任务四 | **`weight_decay`** | **必须是 `0.0`**；如果是 `0.0005`，这条结果的数值不可用 |
| 任务四 | `loss` | 应该是 `bce` |

**为什么这两个字段这么重要？** 因为它们是踩过坑之后才加上的"身份证"：

- 任务三的 `pool_norm=bn` → MaxPooling 会退化成多数类，准确率假性卡住
- 任务四的 `weight_decay=5e-4` → 验证 MRR 从 0.09 掉到 0.0007（差 130 倍），而且**不报错**

加了这两个字段之后，你看结果文件就能一眼分辨哪些能用。详细分析在各任务 README 里。

**看汇总表**：直接跑 `plot_results.py`，它会打印排版好的表格。

## 6. 报告里值得写的东西（这些坑我都验证过了，可以直接用）

作业要求分析"不同网络模型 / 不同参数 / 不同学习率对性能的影响"。
除了那些常规结论，**下面这 6 条是实测发现的真东西**，写进报告比空谈理论有说服力得多：

1. **任务三 · 池化后面接 BatchNorm 会让 MaxPooling 完全失效**（最有价值的一条）
   - 现象：验证准确率死死卡在 0.4054（正好是 PROTEINS 的多数类占比），验证损失反向上涨
   - 原因：BatchNorm 训练用**当前批次**统计量、推理用**累积滑动**统计量，
     而池化图向量的分布会随编码器漂移 → 训练和推理看到的是两个不同的模型
   - 解决：换成 **LayerNorm**（默认已改）→ 准确率回到 0.72~0.77
   - 验证脚本：`python diagnose_pooling.py --dataset PROTEINS --model GAT`

2. **任务三 · MinPooling 是真的退化，不是代码 bug**
   - ReLU 之后节点特征里有大量精确的 0，逐维取最小 → 只要有一个节点是 0，整维就是 0
   - 结果：不同图池化出来的向量几乎一样，分类器没有区分度
   - 这是个**真实的负面结果**，正好解释了为什么实际做图分类几乎没人用 MinPooling

3. **任务四 · 权重衰减必须设成 0**（最隐蔽的一条，因为它不报错）
   - 通用默认值 `5e-4` 对 KGE 是致命的：验证 MRR `0.0007` vs `0` 时的 `0.0936`
   - 原因：Adam 会把"权重衰减"这一项也归一化到 `lr` 量级，
     于是它变成一个和真实梯度**一样大的、恒定把参数往 0 拉的力**，而 KGE 参数几乎全是 embedding

4. **任务四 · 1-N 打分用在 TransE/RotatE 上会"虚假收敛"**
   - 损失降到 0.0168 看起来完美，测试 MRR ≈ 0.0008（等于瞎猜）
   - 原因：距离型模型只要把 `h+r` 推到无穷远，所有分数一起变低，损失就下去了

5. **任务四 · 负采样时不要开标签平滑**
   - 损失死死卡在 `0.3526`：标签平滑把标签从 `1/0` 改成 `0.9/0.1`，
     配 64 个负样本时 BCE 的理论下界就是 `-0.9·ln0.9 - 0.1·ln0.1 ≈ 0.325`

6. **任务一 · 采样训练省的是显存，不是时间**
   - 实测 Flickr：分批次 **2.03 秒/轮** vs 全图 **0.015 秒/轮**
   - 原因：PyG 的邻居采样在 CPU 上搭子图，这个开销比 GPU 算那点东西还大
   - 注意：比较采样和全图时**必须同时看 `steps_per_epoch`**，因为两者一个 epoch 的更新次数差很多
